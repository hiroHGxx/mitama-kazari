## 第0便（2026-08-29）— 骨

**目的は保存が実機で通るかの一点。**通らなければ企画ごと畳む前提で、捨てられる作りにした。

### 実測で確かめたこと

#### 素材蔵は CORS を開けている

```
https://kura.vibe.co.jp/  →  Access-Control-Allow-Origin: *
                              Cache-Control: public, max-age=31536000, immutable
```

`crossOrigin='anonymous'` で読み込めば canvas が汚染されず、`toBlob()` が通る。
**公式の絵を1枚もこちらに置かずに額装できる**——ガイドラインの「素材そのままの再配布
（素材集としての転載）はNG」から構造的にいちばん遠い形。

**`vibe.co.jp/luna-occulta/media/img/canon/` の系統は ACAO を返さない。**
`get_spirit` が返す `sheets` のURLはこちらなので、**canvas に載せるなら素材蔵の側を使う。**
札絵（`fuda`）はそもそも素材蔵にしかない。

#### 札絵の実寸は 1024×1536（2:3）が上限

素材蔵の `fuda_*` も `*_canon` も同じ。`get_spirit` の別系統URLも同値を返す
（**入口を両方当たって確認した**——`kitan-works/docs/KITAN.md` の「無いは入口を全部当たってから言う」）。
これ以上の解像度は存在しない。

対して iPhone 15/16 は **1179×2556**（実機で確認。CSS 393×852 × dpr 3）。

| 合わせ方 | 結果 |
|---|---|
| 幅を合わせる | 高さ1769px。**787px（画面の約31%）が空く** |
| 高さを合わせる | 幅1704px。**左右で約31%を切り落とす** |

**額装は好みではなく必須。**そして額装した時点で二次創作物になる。
技術上の必然と掟の要求が同じ一点を指している——これを企画の芯に据えた。

拡大率は 1179幅で1.15倍。実用の範囲。

### `navigator.share` はタップの資格が切れると弾かれる

iOS は user activation の内側でしか共有シートを開かない。
`canvas.toBlob()` は**非同期**なので、押してから焼くと資格が切れて弾かれる。

→ **File を先に焼いておき、押した瞬間は `navigator.share` を呼ぶだけにした。**
絵を切り替えるたびに焼き直し、焼き終わるまで保存ボタンを伏せる。

### 実機（iPhone・Safari）で通ったこと

| | 結果 |
|---|---|
| 端末の実寸 | 通った（1179×2556 / CSS 393×852 / dpr 3） |
| 素材蔵から crossOrigin で読む | 通った（1024×1536） |
| `toBlob` で書き出す | 通った（3261 KB の PNG） |
| `canShare` が画像を受け取るか | 通った |
| **保存（共有シート）** | **通った。写真アプリに入った** |

**ヘッドレスChromeでは4つ目まで同じ結果が出たが、それはデスクトップChromeの答え。**
iOS の答えは実機を待つまで未決として扱った。

## 踏んだところ

### Artifact プレビューは保存の検証に使えない

閲覧枠がページ側の始める保存（`<a download>`・blob・スクリプト駆動の保存）を塞ぐ。
`navigator.share` も iframe の許可が要る。**通っても落ちても本物の結果にならない。**

`PLAYBOOK.md` の「実機確認は Artifact プレビューでユーザーに投げる」は
**画面と手触りを見る話**であって、保存やダウンロードを測る用途には掛からない。

→ **第0便から GitHub Pages に載せた。**`navigator.share` は HTTPS 必須で、
ローカルサーバーを LAN 経由で開いても（secure context にならないため）通らない。

### プレビューの背が画面を超え、保存ボタンが画面外へ出た

実機で開くと額装プレビューだけで画面が埋まり、オーナーがスクロールして自力で
ボタンを探し当てた。

**`SHITSURAE.md` §6「結果カードの背を伸ばさない」を読んでいたのに踏んだ。**
あれを「結果カードの話」として読んでいたのが原因。**§6は縦に伸びる要素すべてに掛かる。**
端末の縦横比をそのまま持つ要素は、定義上いちばん縦に長い。

→ 枠（`.frame`）を `inline-block` ＋ `height:52vh` ＋ `aspect-ratio`（端末の実寸をJSが入れる）
＋ `max-width:100%` で頭打ちにし、canvas は `width:100%;height:100%` で枠に従わせた。
**寸法は枠側が持つ**（canvas 側に `max-*` を掛けても同じ絵になるが、
枠と中身のどちらが寸法を持つかが曖昧になる）。

### `cd A && ... && cd B` の連鎖でコマンドが別リポジトリに落ちた

`cd mitama-otoshi && git branch -M main` が意図せず走った。
たまたま同値の操作（既に `main`）だったので実害は無かった。

→ **リポジトリを跨ぐ git 操作は `git -C <path>` で書く。**`cd` を連ねない。

## iOS は画面と同寸の壁紙でも、被写体に寄せて自動拡大する（2026-08-29・実機で判明）

**第0便でいちばん大きい発見。**

1179×2556（＝画面と1対1）のPNGを写真アプリから「壁紙に設定」したところ、
**顔が画面いっぱいになるまで自動で拡大された。オーナーは何もしていない**（編集画面を開いた時点でこの寸法）。

同時に **深度エフェクト（被写体を前面に配置）が効いていた**——時計「21:59」の数字の上に髪が被さっている。
iOS が絵を「被写体のいる写真」として解析し、被写体を時計より手前のレイヤーへ置いた。

### 何が壊れたか

**安全域の設計が丸ごと無効になる。** 時計を避けるために上へ空けた宵闇藍の地は、
拡大で画面の外へ追い出される。破線のガイドで確かめた「顔が時計に掛からない」は、
**写真アプリ経由の設定では成り立たない。**

### ただし全部が無駄になるわけではない

| 経路 | 額装が効くか |
|---|---|
| 写真アプリ →「壁紙に設定」 | **効かない**（自動拡大される） |
| 同・編集画面でピンチして縮める | **効く（実機で確認）**。縮めると額装どおりの姿になり、時計が藍色の帯の上に乗る |
| **ショートカットの「壁紙を設定」（第3便）** | **効く見込み**——編集画面を通らないので自動拡大が入らない |
| Android | 自動拡大の仕組みが無い |

**第3便（毎朝ショートカットで替える）は、この問題を回避する経路でもある。**
「自動化のためのおまけ」だと思っていたが、**額装が手を掛けずに届く道**でもある。

### 逃げ道は見つかった。ただし黙っていては誰も辿り着かない

編集画面でピンチして縮めれば額装どおりになる（実機で確認。時計が藍色の帯の上に乗り、
顔にも髪にも掛からない）。**が、この操作を知らない人は自動拡大された姿のまま使う。**

→ 保存ボタンの下に「iOSは勝手に拡大するので、指2本で縮めてください」の案内を常設した。
**知っていれば1手で済むことを、知らせないまま出さない。**

### 蝕環が釦の帯に当たっているのを実機で確認した

縮めた状態のロック画面で、金の輪が懐中電灯とカメラの丸ボタンのすぐ脇を通っていた。
仮説どおり。第2便で置き所を直す（横は両ボタンの間＝画面中央寄りが空いている）。

### 出来上がり自体は良かった

拡大された結果のロック画面は迫力があり、深度エフェクトのおかげで時計との重なりも綺麗だった。
**ただしこれは iOS がやったことで、こちらが設計した結果ではない。**
絵によっては顔が切れる・時計が読めなくなる。**再現できない良さは、設計とは呼べない。**

## 残っている宿題

- **PNG が 3.2MB ある。**共有シートに渡すには重い。JPEG（品質92前後）と比べて第2便で決める
- **蝕環が釦の帯に掛かっている。**足元の闇に置いたが、ロック画面のフラッシュライト／カメラの
  丸ボタンと同じ高さにいる。第2便で置き所を詰める
- **絵の上端に継ぎ目が見える（実機で確認）。**地と絵の境目がまっすぐな線になり、
  「闇から顕れている」ではなく「貼り付けた四角」に見える。原因は2つ:
  ①上端のぼかしを不透明度 **0.85 から**始めているので境目に15%の段差が残る
  ②ぼかしの色を `#131320` 決め打ちにしているが、その高さの実際の地は二色の間（`rgb(22,22,38)` 付近）
  → **絵をオフスクリーンで `destination-out` のグラデーションマスクにかけてから地に載せる。**
  そうすれば地のグラデーションがそのまま透けるので、色の決め打ちが要らなくなる（下端も同じ書き方に揃う）
- ホーム用（アイコンが乗る前提でもう一段沈めた版）を出し分けるか。
  **ロック画面で縮めた設定はホーム画面にもそのまま効く**（下の訂正を参照）ので、
  出し分けるとしたら「必要だから」ではなく「そのほうが良いから」になる

## 訂正: ホーム画面は別のズームを持たない（2026-08-29・同日中に判明）

上で一度「ホーム画面はロック画面と別のズームを持つ。ロックで縮めてもホームは拡大されたまま」と
書いたが、**誤り**。ロックで縮めた設定は**ホームにもそのまま効いていた**。

**アイコンの1行目が藍色の帯をちょうど覆っていたスクリーンショットを見て、帯が無い＝拡大されている、と読んだ。**
アイコンの少ないページのスクリーンショットで、帯も月も御霊の大きさもロック画面と同値だと確認できた。

→ **隠れているものを「無い」と読まない。**画面の写真から地の構成を判定するときは、
**上に何が乗っているか**を先に数える。ロック画面は時計しか乗っていないので読めたが、
ホーム画面はアイコンが乗る。同じ目で見てはいけない。

## 第1便（2026-08-30）— 選ぶ画面

第0便は素材蔵で確認できた5柱を `<select>` に手書きし、深さはスライダーだった。
第1便で **29柱 × 10段の290枚ぜんぶ**に開いた。

### 札絵のURLは組み立てられない（第1便でいちばん効いた発見）

第0便は `KURA + 'fuda_' + id + '_' + depth + '.webp'` と文字列で組み立てていた。
たまたま選んだ5柱（餡音・イズナ・カルマ・ネム・於兎）が全員 `/fuda/` 直下だったので通っていただけで、
**29柱に広げた瞬間に21柱が404になる作りだった。**

宵あらわしが残していた台帳（`yoi-arawashi/scripts/fuda-ledger.json`）の但し書きで気づいた。
実際の分布:

| 型 | 枚数 |
|---|---|
| `/fuda/fuda_<c>_<nn>.webp` | 80 |
| `/fuda/v2/fuda_<c>_<nn>.webp` | 180 |
| `/fuda/v3/fuda_<c>_<nn>.webp` | 10 |
| `/fuda/app/fuda_<c>_<nn>.webp` | 10 |
| `/fuda/v2/fuda_<c>_<nn>_v2.webp` | 8 |
| `/fuda/v2/fuda_<c>_<nn>_v3.webp` | 2 |

**同じ御霊の10枚のなかで型が混ざる柱が6つある**（aun・karura・naruka・oen・orochi・rotton）。
orochi にいたっては1柱で3つの型を持つ。**キャラ単位の規則にすら落ちない。**

→ 台帳を `scripts/fuda-ledger.json` に写し、`scripts/build-roster.js` が
`index.html` の ROSTER 区画へ焼く形にした。焼くのは**台帳のURLから `https://kura.vibe.co.jp/fuda/` を
外した残り**で、画面はそれを前置するだけ。`--check` で焼き直し忘れが落ちる。

**「規則が見えたら規則で書く」を、母数を確かめる前にやらないこと。**
5枚のサンプルは5枚ぶんの証拠しかない。

### 顔アイコンは別ホストにあり、CORS を返さない

選ぶ札に並べる顔アイコン（29枚・各1024²の透過webp）は素材蔵ではなく
`vibe.co.jp/luna-occulta/media/img/canon/<id>_icon.webp` にある。ここは ACAO を返さない。

**それで構わない。canvas に載せないなら CORS は要らない。**`<img>` で表示するだけなら
汚染も何も起きない。第0便の「ACAO を返さない系統は使えない」という結論は
**canvas に載せる場合の話**であって、表示一般の話ではなかった。同じ素材でも、
**どう使うかで掛かる制約が変わる。**

29枚で合計2.58MB（平均91KB）あるので `loading="lazy"` にし、札を送ったぶんだけ取る。

### 画面

- **御霊を選ぶのは「開いて閉じる札」にした**（SHITSURAE §7）。29柱を本体に並べると
  縦に700px超になり、「写真に保存」がまた画面外へ出る。御霊おとしの図鑑・番付と
  帳・角丸・✕・外側タップ・Esc まで同じ作法にしてある
- **深さは10個の帯**（御霊おとしの階梯と同じ形）。幅390pxで44px×10は入らないので
  押し所は24pxを床に詰めた（実測31.0px／SE で29.2px）
- 選んだ印は**金泥の面**で出す。**輪では出さない**——円の光り物は蝕環ひとつだけ、という
  公式トンマナの決まりがあるため
- 枠（プレビュー）は 52vh → **44vh** へ譲った。下に帯が2本増えたぶん。
  背の低い画面（`max-height:700px`）では 37vh

### 連打で古い絵が後から乗る穴を塞いだ

札絵は100〜350KBあり、読み込みは非同期。第0便は選び直しに番号を持っていなかったので、
**続けて押すと古い読み込みが後から返って新しい絵を上書きしうる**作りだった
（第0便はスライダーの `change` だけを見ていたので表に出なかった）。
`seq` を1つ持ち、`loadFuda` の解決時と `toBlob` の解決時の両方で締める。

### 実測（`scripts/check-layout.js`）

第0便で「保存ボタンが画面外へ出た」のを二度踏まないため、押し所の位置を毎回機械で測る。

| 見たもの | 結果 |
|---|---|
| 「写真に保存」が最初の画面に収まる | 393×740 で余り64px／375×560 で余り25px／393×852 で余り127px |
| 押し所 24px の床 | 深さの帯 最小29.2px・選ぶ入口 319×58px |
| 文字 12px の床 | 最小12px |
| 顔アイコン29柱 | 29/29 表示 |
| 札絵4系統＋ファイル名変種 | 7通りすべて読めて `toBlob` も通った（canvas は汚れていない） |
| 連打 | 最後に押した段に落ち着き、控えも一致 |
| `localStorage` が例外を投げる環境 | 最後まで動く |

**高さは「iOS Safari の上下バーが出ている時の実効値」で測る。**852 や 667 は全画面の値で、
実際に見えているのはそれより低い。第0便はそこを見ていなかった。

### 残っている宿題（第2便へ持ち越し）

第1便は選ぶところまで。**額装の質は一切触っていない。**

- **絵の上端の継ぎ目**（画面でも確認できる）。ぼかしを 0.85 から始めているので境目に15%の段差が残り、
  色も `#131320` 決め打ちで地のグラデーションと合わない
  → オフスクリーンで `destination-out` のマスクにかけてから地に載せる
- **蝕環がロック画面の釦の帯に掛かっている**
- **PNG が 2.5〜4.2MB**（柱と段で変わる）。JPEG（品質92前後）と比べて決める
- ホーム用にもう一段沈めた版を出し分けるか
